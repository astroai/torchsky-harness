# torchsky 0.4.0 / harness 0.1.0 completion plan

Status: **draft for audit**. No code changes are implied by this document.
Date: 2026-10-21. Owner: Lead; external reviewer: user.

This is the plan to take the reworked subject from “strong core with green
release evidence” to a defensible **full functionality replacement for the
WCS/coordinate, sphere/HEALPix, and mapmaking domains (inventory sections 2–4)**,
with the remaining ecosystem packages either explicitly compatible, explicitly
out of scope, or scheduled after 0.4.0.

## 1. Completion definitions

### 1.1 Release gate (must all be true)

1. All declared release gates pass at one frozen subject artifact and one
   frozen harness revision; `release_ready: true`, no missing/incomplete claims.
2. Sections 2–4 are workflow-complete against the replacement matrix below:
   every “replacement-required” capability has either a passing comparator gate
   or a written, audited exception.
3. Native contracts and fuzz gates pass; no known crash/hang/silent-wrong
   class remains.
4. Full subject suite, examples, docs build/contract, typecheck, and installed
   wheel smoke are green; docs site builds strict.
5. CI-built wheel and sdist pass distribution/linkage/license checks on Linux
   and macOS; one canonical publish workflow exists.
6. GPU/CANFAR evidence is green for the final subject, with any known
   device-specific tolerance documented and accepted.
7. No public API duplicate/legacy surface remains without an explicit,
   audited deprecation/removal decision.

### 1.2 Replacement definitions

- **Workflow replacement**: a representative user workflow can run on torchsky
  without the peer package and produces equivalent scientific results.
- **API replacement**: torchsky exposes the peer’s public objects/functions
  under compatible names (required only where explicitly decided, e.g. a
  healpy compatibility layer).
- **Interop boundary**: the peer survives only as an optional adapter (e.g.
  live GWCS objects), and the boundary is documented and tested.
- **Out of scope**: named in the audit sign-off; not silently omitted.

### 1.3 Audit decision needed (D1)

The two plausible release scopes:

| Scope | Content | Recommendation |
|---|---|---|
| A. Core replacement release | Sections 2–4 fully replaced; sections 5–8 (source detection, photometry/PSF/deblending, spectral/cosmology/extinction/catalog gaps) remain post-0.4.0 | Recommended if 0.4.0 is a compute-engine release |
| B. Full-stack replacement release | Everything in the replacement inventory, including sections 5–8 and the planned high-energy/radio peers | Requires a much longer program; only if the release is defined as a full astronomy-stack replacement |

The rest of this plan assumes A unless the audit chooses B.

## 5. Audit decisions required

- **D1 Release scope**: choose A (core replacement) or B (full-stack replacement).
- **D2 Compatibility depth**: for healpy, astropy-healpix, healsparse, mocpy,
  which APIs must be name-compatible vs workflow-equivalent?
- **D3 Astrometric solver**: is `SCAMP`/`tweakreg` parity required, and is a
  blind `Astrometry.net`-class solver in scope?
- **D4 GWCS/PyAST**: implement a general transform graph/object model, or
  accept a documented interop boundary?
- **D5 Real data**: which datasets may be vendored/pinned, and what is the
  licensing/provenance policy?
- **D6 SHT backends**: is `s2fft`/`ducc0` interchangeability required, or
  optional performance comparison only?
- **D7 CMB/radio/high-energy**: explicitly out of 0.4.0, or required?
- **D8 Big-file exceptions**: approve the line threshold and any cohesive file
  that may remain above it.
- **D9 Release/PyPI**: confirm no PyPI until the release gate, and choose the
  canonical publishing workflow.

## 6. Risks and controls

| Risk | Control |
|---|---|
| Splits break public imports or numerical behavior | move-only commits; facade exports; full suite + gates; API diff |
| Replacement scope balloons | D1/D7 scope sign-off; explicit out-of-scope list |
| External comparator unavailable on macOS | certify on Linux/CANFAR; local runs are development only |
| GPU/device tolerances hide regressions | documented tolerances; CPU parity tests where applicable; device gate per release |
| Real-data licensing/redistribution | pinned external durable storage + manifests; no committed raw survey pixels |
| Evidence revision drift | freeze subject/harness before final bundle; rerun all claims at frozen revision |
| Can’t finish full-stack before release | scope A release; sections 5–8 remain explicit post-release work |

## 7. Change control

Any change to a frozen tolerance, claim set, API removal, or replacement scope
requires an audit-log entry with rationale and reviewer sign-off. Every code
change must name the workstream ID in its commit message and record verification
commands/results in the audit log.
